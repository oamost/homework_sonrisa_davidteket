# Goals

**Feature status: FROZEN — human-approved scope.** Implementation details and open feasibility questions are addressed task by task; changes to these goals require explicit human direction.

## Original requirement (verbatim)

> "We want users to be able to set up alerts so they get notified when something important happens in the world — like breaking news, market movements, natural disasters, that kind of thing. Should work for both email and Slack. Make it flexible enough that we can add more channels later. We need an admin view too."

## Documented plan

This is the human-readable counterpart to the deliverable matrices in `ctx/goals/tasks.md`. The human-approved preparation and discovery work (Deliverables 1 and 2) established the repository conventions, prompt history, initial source evidence, approved event-category coverage matrix and the agreed local runtime direction. Those completed tasks are recorded in the tracker rather than replayed here as setup instructions. The remaining work is Deliverable 3: **the complete in-house world-event alert application**, not a one-source demonstration or a service designed for commercial scale. The human chooses which task to address next; open details are settled with the human as the relevant task is worked, not assumed to be approved in advance.

**Agree the behavior and establish the local foundation (Deliverable 3, tasks 01–04).** First, work through concrete examples and acceptance decisions for what counts as important in each event family, how 24-hour eligibility is dated, how to pace and retry alerts, what belongs behind the admin wall, and how a new delivery platform is configured without changing production code. Build a locally runnable C# application and its test foundation with persistent SQLite and an **Angular frontend** for alert setup and admin, as selected by the human. Each person runs their own copy. Persist subscriptions to an event type from the approved matrix and the user's chosen notification channels; a subscribed user is notified when an important event in that type occurs. Record source identity, category, region, relevant event and publication times, metadata and provenance, including how missing or conflicting timestamps are handled, so news, market, disaster and other approved events can be handled consistently. No per-instrument or per-source custom rule is an agreed requirement.

**Find and integrate the required events (tasks 05–11).** Validate keyless, no-registration event sources for worldwide breaking news, major disaster types across all regions, and worldwide market movements, then ingest and normalize them. The approved coverage direction also includes armed conflict and politics, diplomacy, public health and humanitarian emergencies, macroeconomy, AI/cybersecurity/breaches/major acquisitions and critical infrastructure, environment and energy, and transformative science or inventions with lasting impact. Evaluate access, freshness, geographic and type coverage, attribution and historical availability before relying on a source; a sampled news feed, crypto rate or disaster type does not establish exhaustive global or 24-hour coverage. Document gaps and investigate alternatives rather than narrowing the goal silently. A source that refuses a probe is blacklisted and not retried; GDELT, ReliefWeb v1, the probed Meteoalarm endpoint and Stooq are already blacklisted. Email and Slack delivery credentials are separate from the prohibition on event-source accounts or API keys.

**Collect, assess and match events (tasks 12–17).** While the local app runs, poll working sources at appropriate cadences without duplicate concurrent pollers, preserve progress and surface stale or failed sources. Deduplicate repeated stories or observations across sources and restarts while respecting genuine event updates. Determine importance and breaking relevance with deterministic, multi-factor, metadata-informed methods for news, market movements and disasters, using human-reviewed examples; not every new article is important, and the earlier illustrative 0–1 *category* scores are not measured per-event scores or approved thresholds. Match important events to subscriptions and their configured channels, including the approved additional event families.

**Catch up and send without flooding (tasks 18–22).** On startup, look back over the previous 24 hours for important, not-yet-delivered events in **every defined category**, including news, markets, disasters and the other approved types, even if the machine was off. A feed that publishes late should still produce a normal notification. Persist pending deliveries, prevent repeats, pace catch-up and simultaneous events so users are not overwhelmed, and use reasonable, non-excessive retries. The human relaxed the earlier unconditional under-five-minutes-from-real-world-occurrence demand for late feeds and catch-up; the precise timing, timestamp interpretation, deduplication and pacing choices remain to be worked out, and source support for full 24-hour recovery is unverified. Support email through configured SMTP credentials and Slack through an authorized, privately stored incoming webhook. Also make it possible to add a platform not pre-coded in the app **without changing production code**, with the specific safe configuration/integration mechanism decided during its task.

**Make it usable and operate it locally (tasks 23–26).** Provide a frontend where a local user can see the available event types, choose subscriptions and delivery channels, and understand their alerts. Provide a protected admin view for the operational functions the human agrees belong behind an admin wall; its exact authority and contents are not silently assumed. Protect delivery secrets, prevent duplicate running processes and preserve SQLite state across normal restarts; agree on a suitable recovery or backup approach. Place Linux and Windows launch scripts in the repository's **top-level directory** so either platform follows the same containerized **build → test → run** path, stops on a test failure and can be rerun idempotently. The location does not imply root or administrator privileges for the scripts; Docker access must be configured. GitHub Actions remains off; GitHub does not host the running app.

**Prove and explain each feature as work progresses (tasks 27–30 and every implementation task).** Unit-test non-trivial methods and integration-test major functions. Maintain a feature-to-unit/integration-test inventory that shows what actually has test coverage, and add each implemented user-facing feature to a user guide as it arrives; verify the guide against a fresh local installation. Every implementation task produces appropriate evidence under `docs/`, such as logs or redacted screenshots; code and tests belong in `src/` and produced artifacts in `out/`. Demonstrate end-to-end subscriptions, importance decisions for every family, all-category 24-hour catch-up, late items, pacing and retries, SMTP, Slack, a newly configured channel, the admin wall and local startup on Linux and Windows, while disclosing any remaining provider limitations. A task is `TESTING` after agent checks and `DONE` only after human verification; a milestone commit needs separate human approval.

The approved source-coverage matrix in `docs/requirement-coverage.md` is evidence and direction, not proof that every feed or historical window works in production. Remaining matching, source and acceptance decisions are addressed task by task with the human without silently weakening the original goal. `ctx/goals/tasks.md` remains the detailed status-and-evidence tracker; this section describes its combined intent without duplicating its task matrix.
