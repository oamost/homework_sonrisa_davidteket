# Seamless world-event feed and notification setup — approved design

## Intent and scope

Make the existing local Angular/C# application useful without manual refreshes or one-subscription-at-a-time setup. A new local user follows all currently approved event types by default, may edit that choice as compact tags, and receives qualifying alerts through every configured channel. Email and Slack setup and a public-but-bounded synthetic test event should be straightforward. Preserve the existing event/score provenance, SQLite state, admin wall, approved 24-hour eligibility and bounded delivery queue.

The human approved this design, including a configurable generic webhook channel. This is not yet implemented. It covers the eight changes requested after reviewing screenshots. Previously recorded provider limits, missing baselines and secret-handling obligations remain visible.

## Home feed

- On page load and at a modest interval (engineering default: every 60 seconds while visible), request the existing persisted-data event preview. No user refresh button; stop timers on navigation, avoid overlapping requests, and show the last successful update, loading/empty/stale/error state without fabricating events. Provider polling continues on its separate configured cadence.
- A small **Debug** checkbox is visible near the heading. The entire diagnostic block marked in the screenshot—counts, event-type counts, family statistics, baseline warnings, omitted/rejected counts, coverage gaps and update-time diagnostics—is hidden by default and appears only while checked. Ordinary event cards retain readable title, family, source, provider time and links. Debug may additionally reveal the actual finite 0–1 score, rule and factors, labelled as heuristic strength, not factual confidence.
- A **Send test event** button appears only when Debug is checked. The button makes an explicit same-origin POST that anyone who can access the local page may use; admin login is **not** required. The server protects it with a same-origin/CSRF check and a durable global cooldown/daily cap so a public page cannot become a notification spam relay. Response exposes no addresses, webhooks or provider credentials. Rejected or rate-limited attempts explain why without leaking recipient state.
- Each successful click creates a unique, visibly **TEST — not real news** synthetic `world-news` event with server-issued provider-equivalent timestamp and a clearly designated test importance decision above the publication threshold. It is persisted/queued by the existing path, expires from the public feed after a short interval (engineering default: 5 minutes), and sends only to **configured channels whose saved event-type selection includes `world-news`**. If `world-news` was removed, no channel receives it; show a safe explanatory result instead of bypassing preferences. Do not fetch a provider, generate a fake real headline, or bypass rate limits/retry/duplicate protections.

## Alert setup

- For a **new local user without saved preferences**, all currently approved types (including `economy.financial`) are selected by default. Render compact adjacent clickable tags that toggle inclusion. One Save action persists the chosen set, including intentionally empty selections; returning/restarting displays the saved set. An already customized installation keeps its existing choices until its owner saves the new global selection—never silently broaden old recipients. A newly approved type becomes a default only for a new, uncustomized user; show it as unselected for existing customized users until chosen.
- The saved event-type set applies to **every configured channel**. A channel lacking valid credentials/destination is visibly `Needs setup`, not `disabled`; it cannot send until configured. Once configured, it begins automatic delivery immediately, including eligible catch-up, without a separate activation switch or mandatory test. The independent **Send test** action remains available at any time. State the startup burst (at most 50 then at most 10/minute), provider gaps and meaning of the importance score plainly.
- Email and Slack have parallel, short setup cards with redacted connection status, understandable validation errors and direct testing affordances. Email addresses, sender address, SMTP username and non-secret Slack channel names are **readable text/email fields**, not password inputs. SMTP password and the incoming Slack webhook URL are **secrets**: keep them in password-type fields with an optional temporary reveal of entered text, never display saved values or store them in source control, browser storage or plaintext subscription destinations. The browser never assumes that being signed into email or Slack supplies SMTP credentials or a webhook. Explain the needed app-password/SMTP service or Slack incoming-webhook creation/install in-place without requiring secrets in chat.
- Use the already protected per-person server-side settings and persistent Data Protection keys; make Slack's existing protected store/API/transport reachable from the host, put its setup into Alert setup, and connect Slack jobs to the same persistent queue and bounded retries as email. Adding/removing a tag updates matching for all configured channels transactionally. Existing channel-specific legacy rows remain effective until explicitly migrated by the user; do not reinterpret a missing row as permission to send to an old recipient.

## Future channel mechanism

- Expose a documented **generic webhook channel** configured without editing production code: HTTPS URL, method, approved headers, JSON body template and explicit test-send. Credentials are protected server-side; outbound destination validation blocks local/private network endpoints and redirects by default. Registered channel identifiers and non-secret labels can appear alongside email and Slack; disabled/unconfigured channels cannot send. Use the existing persistent queue, approved pacing and retries; do not claim an untested arbitrary platform is working.

## Admin operations

- Reload the protected source-health/poll-status and queue/failure snapshot automatically (engineering default: every 30 seconds while visible), with last successful refresh, stopped/stale/unavailable states and safe retry on network errors. Do not label a disabled source poller healthy or invent zero source rows. Keep authenticated cookies, CSRF-protected mutations and redaction; no full destination, SMTP password or Slack webhook appears. Stop on logout/navigation.

## Acceptance evidence and boundaries

- Unit/integration tests: first-run all-selected versus customized/empty saved state and legacy migration; toggling/saving/reloading tags; each configured channel following the same saved set; readable non-secret fields versus masked protected secrets; Slack/email authorized setup and one-attempt test-send; startup catch-up and queue pacing; test event only when `world-news` is selected, delivered once to all configured channels, durable cooldown, CSRF rejection, no leaked recipient; timer cleanup/non-overlap and failed refresh in feed/admin; config-only example generic webhook with fake HTTP handler. No external SMTP/Slack sends in automated tests.
- Manual review: home/debug before and after toggle, compact tags on a fresh and customized profile, real email/Slack test sends **only after the human configures and consents**, and admin refresh. SMTP acceptance is not proof of inbox delivery; signed-in Slack alone is not an authorized incoming webhook. Native Windows and global provider coverage remain separate limitations.
- The earlier human proposal to use **score > 0.70** as one common publication/delivery gate needs explicit cross-family calibration; do not silently turn already accepted boolean family rules into different semantics in this UI change. Show the numeric score and the current rule faithfully until the threshold is separately frozen and tested.
