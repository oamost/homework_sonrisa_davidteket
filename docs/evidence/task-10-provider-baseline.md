# Task 10: Binance provider baseline

The Binance `24hr` ticker payload already contains `lastPrice`, `openPrice`, `openTime`, and `closeTime` in one response. The parser now retains `openPrice` as `BaselineValue`, `openTime` as `BaselineUtc`, and `rolling-24h-open` as `ComparisonKind`, but only when the price is finite and positive, all timestamps parse, the source interval is `24h`, and the timestamp span is within one minute of 24 hours (rolling-window alignment). `ObservationUtc` remains `closeTime`, and `Value` remains `lastPrice`. This is **not** a previous UTC-day close. For a percent movement compare `(Value - BaselineValue) / BaselineValue * 100`; only use this comparison when all three baseline fields are present and `ComparisonKind == "rolling-24h-open"`.

Missing, invalid, or mismatched baseline fields leave the observation baseline fields null. `MarketParseResult.BaselineDiagnostic` explains why; a valid baseline returns null. No additional Binance provider request is issued.

SQLite schema initialization adds nullable `BaselineValue`, `BaselineUtc`, and `ComparisonKind` columns to existing tables idempotently. Old rows retain nulls; no historical price is inferred. A repeat provider poll with the same `(SourceId, Instrument, Interval, ObservationUtc)` can populate an entirely missing baseline without changing the existing row's value/fetch time or incrementing insertion count. Historical rows require a same-identity provider re-poll to gain baselines; otherwise they remain unavailable for provider-baseline comparison. New observations persist metadata and selection/recent reads round-trip it.
