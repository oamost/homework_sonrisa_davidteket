# Task 23 — alert-setup frontend evidence (awaiting human verification)

## Scope and integration

- Standalone `SubscriptionsComponent` in `src/web/src/app/subscriptions/subscriptions.component.ts`; root route/navigation are owned by another worker. It uses the existing `GET`, `POST` (upsert by event type and channel), and `DELETE /api/subscriptions/{id}` endpoints, with no new API or dependencies.
- Shows all 23 D1-approved event codes with display names and descriptions, including qualified source-coverage notes. No instrument/location/threshold configuration is offered.
- Validates email addresses and non-secret Slack channel references (`channel:#name`) before POST. Destination input is masked and not rendered in the saved list, URLs, logs or browser storage. Existing destinations are only kept in the in-memory API response to allow a blank edit to preserve the value on upsert. Delete requires a second explicit confirmation. Save/delete controls disable while a request is in flight; load, save, delete, empty and retry states are displayed without server response bodies.
- **Security and delivery limitation:** The current API stores `destination` in a plain SQLite column and returns it from GET/POST. Its `Subscription` model explicitly says this field must never hold a credential. Therefore a Slack *webhook URL must not be pasted into this setup*; the form rejects webhook URLs and accepts only a non-secret channel reference, while the real webhook belongs in private server configuration. This reference does **not** wire a particular saved subscription to a sender. The UI explicitly states that queue/sender integration is unfinished and no active delivery or worldwide/24-hour completeness is promised. Email addresses are likewise returned by the API even though this UI does not render them; privacy beyond the UI requires backend changes outside task 23.
