# Email delivery setup and safety

Email notifications are off until a local administrator explicitly saves and enables SMTP in **Alert setup**. Sign in through `/admin/login` using the existing admin password, return to Alert setup and configure SMTP host, port (normally 587), username, password, and From address. STARTTLS is mandatory; implicit TLS on port 465 is unsupported. Save with **Enable automatic email delivery** checked only when you want pending eligible email notifications to start sending. Add an enabled email subscription with a valid destination for each desired event type. To perform a single test send, explicitly enter a destination in the admin-only test field and press **Send test email**; SMTP acceptance does not prove inbox delivery. No network SMTP test is run automatically.

Private settings are Data Protection-encrypted at `<WorldAlerts:DatabasePath>.email.protected`; encryption keys are persisted at `<WorldAlerts:DatabasePath>.keys/`. The default DB location is `src/api/data/worldalerts.sqlite` when running the API from `src/api`. Ensure both files and keys are persisted across deployments, writable only by the server account, backed up together, and **excluded from source control**; losing keys makes settings unreadable and requires reconfiguration. API responses redact the password and username; submitting a blank password keeps the existing password. Do not place SMTP credentials in appsettings, a subscription destination, browser local storage, or screenshots. Provide the admin password hash through the existing server-side configuration. Admin login is required to view status or change settings; changing or testing also requires the CSRF token from the authenticated status request.

Selection runs at first enabled startup and then once per minute. The preexisting durable queue allows up to 50 notifications in an initial burst and 10 per rolling minute thereafter, with retries at 1, 5 and 15 minutes and a terminal failed state. An interrupted send is marked `uncertain` on restart and not replayed automatically: a provider may have accepted it even without a local acknowledgement. Administrators must manually investigate uncertain records. Pausing SMTP stops further background claims; an in-progress SMTP call may still complete. Slack is separate and disabled from the email dispatch path; saved Slack subscriptions are retained.

No real mail is sent by automated tests. Live SMTP configuration, actual provider acceptance, eventual inbox delivery, source coverage, and actual event selection must be verified by the human with their own SMTP account and chosen destination. Automatic notification selection depends on canonical native event identity matching between the existing selector and stored records; unmatched preview records are deliberately skipped rather than fuzzy-matched.
