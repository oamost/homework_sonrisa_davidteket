# Local startup (task 26)

Prerequisites: a Docker Engine accessible to the current user (`docker info`). **Docker Compose is not required.** Running the launch scripts as root/Administrator is not required. Docker daemon access must be provisioned separately and itself grants powerful host privileges. Docker Desktop with Linux containers is suitable on Windows; run `run.ps1` from PowerShell. On Linux, run `./run.sh` (or `bash run.sh`). Do not run both at once while the other is building.

1. Create a private env file at the repository root named `.env` (ignored by Git), or point `WORLDALERTS_ENV_FILE` at an existing private env file. On Linux restrict file permissions, e.g. `chmod 600 .env`. The file can contain ASP.NET configuration environment variables such as `WorldAlerts__Delivery__Smtp__...` and `WorldAlerts__Delivery__Slack__WebhookUrl`; provide only credentials and channels you intend to use. Do not put secrets in `src/api/appsettings.json` or the container image. Do not check `.env` into Git. An empty `.env` is valid for API-only testing without configured delivery. Docker Engine consumes the file at **runtime**, not at build time. For offline smoke checks with no real provider requests, include all four settings `WorldAlerts__News__PollingEnabled=false`, `WorldAlerts__Markets__PollingEnabled=false`, `WorldAlerts__Disasters__PollingEnabled=false`, and `WorldAlerts__Advisories__PollingEnabled=false` on separate lines.
2. From any directory, invoke the script in this repository. Both scripts invoke `docker build --no-cache -f src/container/Dockerfile` then run the resulting image with Docker Engine. The Dockerfile builds the .NET 10 solution, executes the actual `dotnet test src/WorldAlerts.sln` suite, and publishes the API. Only a successful image build can reach volume/container operations. Re-running stops and replaces **only its own labeled named container**, rather than starting a duplicate; a failed build/test does not launch or replace it. An already-running instance remains running on a failed rebuild. A later `docker run` failure after a successful build and stop is reported as a failure (the container may need a subsequent relaunch).
3. Visit `http://127.0.0.1:8080/api/health` to check API health, or `http://127.0.0.1:8080/` for the current API root. The existing Angular project is not served by this API image; no integrated static UI hosting is present in the API yet, so a local UI screenshot is not evidence of this container alone. When frontend integration is ready, its hosting needs separate verification.

The container runs as the non-root `app` user; only localhost port 8080 is published by default. SQLite uses `/app/data/worldalerts.sqlite` in the Engine-managed **named volume** `worldalerts-local-data`, preserved across rerun/rebuild. ASP.NET data-protection keys are in the separate named volume `worldalerts-local-keys` so session protection survives container replacement. Treat the keys volume as **private**: the current .NET deployment logs that its keys are not encrypted at rest, so restrict Docker access and safeguard backups of both volumes. The separate private env file is never baked into the image. Do not remove either volume to perform a normal restart. For a consistent backup, stop the service (`docker container stop worldalerts-local`) before copying the database/volumes through your approved Docker backup process; save the separate private env file securely. A raw copy while SQLite is active can be inconsistent, especially with WAL files. Restore both volumes and private config before startup. No backup automation is supplied here.

To stop without deleting volumes, use `docker container stop worldalerts-local`. To diagnose a failed build, inspect its output; do not run an old image manually to bypass failing tests. The default container is `worldalerts-local`; set `WORLDALERTS_INSTANCE` to another lowercase Docker-safe name and `WORLDALERTS_PORT` to another available loopback port to keep independent instances apart. The volumes are `<instance>-data` and `<instance>-keys`. A different instance name does **not** share the default SQLite state. Both scripts reject existing containers or volumes without matching ownership labels rather than overwriting them. GitHub Actions and cloud hosting are not involved.
